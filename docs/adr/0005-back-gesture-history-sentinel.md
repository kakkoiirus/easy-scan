# Intercept the back gesture via a browser-history sentinel

Easy-scan's UI is a pure in-memory screen state machine in `App.tsx` — `library ↔ camera ↔ document` — with no router and no use of the History API. So the phone's back gesture (Android system back, or a browser tab's back/swipe-from-edge) never reached the in-app `onBack` handlers: it popped the browser history, which is empty, and the platform did its default — minimizing/exiting the installed PWA or navigating to the previous site. To make back behave like an in-app "up" button, we mirror the screen stack onto `window.history`: when the current screen is anything but `library`, a single sentinel entry is pushed (`history.pushState` with **no URL change**), and the `popstate` handler calls the current screen's existing `onBack`. `library`, the root, pushes nothing, so back there honestly exits the app — the expected PWA root behaviour.

**Why:** gesture-based navigation is the phone habit; "back exits the app mid-scan" reads as a bug. The fix had to route the gesture into the existing `onBack` chain without introducing server-side routing — there is no backend (ADR-0001) — and without breaking the GitHub Pages subpath deploy (ADR-0004).

**Trade-offs accepted:**
- **Sentinel, not a real URL.** The history entry carries no path/hash, so the address bar never changes and **refresh always lands on `library`**. This is deliberate: the Pages subpath has no SPA fallback, so a path like `/document/<id>` would 404 on refresh (ADR-0004); and the camera screen is ephemeral — a mid-capture stream and unsaved batch cannot be restored, so dropping to `library` is the only sane refresh target. The cost is no deep links and no URL that reflects the screen: invisible in `standalone` mode (no address bar), and in-browser the gesture still works, just without a changing URL.
- **A confirm guards camera back when pages are unsaved.** Nothing is persisted until "Готово" — back discards the *entire* batch. The on-screen button already relabels to "Отмена" once a shot is taken, signalling that this is destructive; making the *gesture* work makes it reflexive and accidental-prone, so the first back with captured pages in flight shows a confirm ("Сбросить N страниц?"), while an empty session backs out instantly. The confirm lives in `CameraScreen`, where the unsaved state lives; `document` needs no guard because its edits persist to the store live.
- **iOS Home-Screen PWA is out of scope.** Standalone iOS has no system back gesture to intercept; those users already navigate via the on-screen back buttons, which are unaffected.

**Rejected alternatives:** hash routing (`#/camera`, `#/document/<id>`) — survives refresh, but the camera can't be restored and document deep-linking is a feature nobody asked for, so the URL noise buys nothing here; real path routing — needs a server SPA fallback and 404s on the Pages subpath (ADR-0004); no guard (back always discards) — consistent with "Отмена" but the gesture is too accidental for silent multi-page loss; back-as-save (treat the gesture as "Готово") — surprises users who read back as cancel.
